Parte I

Lógica de programação com Dart

A base de tudo: como um programa pensa, guarda valores, decide e repete.

1. Algoritmo, variáveis e tipos

Um algoritmo é uma sequência de passos para resolver um problema, como uma receita de bolo. Um programa é um algoritmo escrito numa linguagem que o computador entende. Todo algoritmo tem três partes: entrada (o que ele recebe), processamento (o que faz com isso) e saída (o resultado).

Exemplo geral 
// Entrada: preço e quantidade. Processamento: multiplicar. Saída: total.
double preco = 25.0;
int quantidade = 4;
double total = preco * quantidade;
print('Total: R\$ $total');   // Total: R$ 100.0

Variáveis

Null safety: o valor "vazio"

null significa "sem valor". O Dart obriga você a dizer quando uma variável pode ficar vazia, colocando ? no tipo. Isso evita o erro mais comum da programação: usar algo que não existe.

int idade = 20;      // nunca pode ser null
int? idBanco;        // pode ser null (ainda não foi gravado no banco)

idBanco ?? 0         // ??  "se for null, use 0"
texto?.trim()        // ?.  "só chama trim() se não for null"
org ??= outro;       // ??= "se org for null, coloque outro nele"
valor!               // !   "garanto que não é null" (se for, o programa quebra)

O resto % é muito usado em lógica. n % 2 == 0 diz se um número é par. n % 15 == 0 diz se ele é múltiplo de 15. O seu projeto usa os dois tipos de ideia: no CPF (soma % 11) e na contagem regressiva (restante % 15).

Os operadores lógicos param cedo ("curto-circuito"). Em a && b, se a for falso, o Dart nem olha o b. É por isso que valor != null && valor < 1 nunca quebra: se for null, a segunda parte não roda.

5. Funções

Uma função é um bloco de código com nome, que você chama quando precisa. Ela evita repetir código e divide um problema grande em pedaços pequenos.

// tipo de retorno · nome · parâmetros
double media(double a, double b) {
  return (a + b) / 2;
}

// Arrow function: quando a função só devolve uma expressão
double media2(double a, double b) => (a + b) / 2;

// void: a função não devolve nada
void saudar(String nome) {
  print('Olá, $nome');
}

Os três tipos de parâmetro

// 1) Posicionais: a ordem importa
int somar(int a, int b) => a + b;
somar(2, 3);

// 2) Nomeados, entre { }: quem chama escreve o nome
void criar({required String nome, int idade = 0}) {}
criar(nome: 'Ana', idade: 30);
criar(nome: 'Bruno');              // idade usa o padrão 0

// 3) Posicionais opcionais, entre [ ]
String titulo(String nome, [String? sobrenome]) => '$nome ${sobrenome ?? ''}';

Um parâmetro posicional (quantidade) e um nomeado obrigatório (aplicarEspera). Ao ler _rodada(3, aplicarEspera: true), fica claro o que o true significa. Com _rodada(3, true), ninguém saberia.

Onde está a lógica no seu projeto

Os trechos do App de Eventos em que o programa decide, repete e calcula, com teste de mesa.

Um teste de mesa é executar o algoritmo "à mão", anotando o valor de cada variável a cada passo. É a melhor forma de provar que a lógica está certa, e professores costumam pedir.

1. O menu: laço + decisão

2. O login: contadores e estados

lib/login.dart
Future<Organizador?> executarLogin() async {
  while (true) {
    var org = await _rodada(tentativasIniciais, aplicarEspera: true);   // 3 tentativas
    org ??= await _rodada(tentativasAposEspera, aplicarEspera: false);  // +2 se falhou
    if (org != null) {
      ...
      return org;                     // sucesso: sai do laço
    }
    final senhaTrocada = await _esqueciASenha();
    if (!senhaTrocada) return null;   // desistiu: sai
  }                                   // trocou a senha: volta ao começo
}

A lógica forma uma sequência de estados:

  1. Rodada 1: até 3 tentativas. Se errar as 3, o e-mail fica bloqueado por 60 segundos (gravado no banco).
  2. Rodada 2: mais 2 tentativas, sem novo bloqueio. O ??= só roda esta rodada se a primeira devolveu null.
  3. Esqueci a senha: até 3 chances de confirmar nome e e-mail e cadastrar uma senha nova.
  4. Recomeça do passo 1 com a senha nova, graças ao while (true).

Dentro de _rodada, um for (int i = 1; i <= quantidade; i++) conta as tentativas, e a condição aplicarEspera && i == quantidade detecta "errou a última tentativa da primeira rodada".

Segurança dentro da lógica: a senha nunca é comparada como texto. A função senhaConfere usa o bcrypt para comparar a senha digitada com o hash guardado no banco.

4. A validação de CPF: um algoritmo clássico

lib/validacao.dart
bool cpfValido(String cpf) {
  final digitos = cpf.replaceAll(RegExp(r'[^0-9]'), '');      // 1) só números
  if (digitos.length != 11) return false;                     // 2) precisa de 11
  if (RegExp(r'^(\d)\1*$').hasMatch(digitos)) return false;   // 3) 111.111.111-11 não vale

  List<int> nums = digitos.split('').map(int.parse).toList();  // 4) texto → lista de int

  int calcularDigito(List<int> base, int pesoInicial) {
    int soma = 0;
    for (int i = 0; i < base.length; i++) {
      soma += base[i] * (pesoInicial - i);                     // 5) soma ponderada
    }
    int resto = soma % 11;
    return resto < 2 ? 0 : 11 - resto;                         // 6) regra do dígito
  }

  int primeiroDigito = calcularDigito(nums.sublist(0, 9), 10);
  int segundoDigito = calcularDigito(nums.sublist(0, 10), 11);
  return primeiroDigito == nums[9] && segundoDigito == nums[10]; // 7) confere
}

Aqui aparece quase toda a lógica de programação junta: limpeza da entrada, condições de saída antecipada (return false), conversão de tipos, laço com acumulador, operador %, ternário e operador lógico &&.

Parte III

Programação Orientada a Objetos (POO)

A forma de organizar o código em "coisas" que têm dados e comportamentos.

1. Classe e objeto

A classe é o molde (a planta da casa). O objeto é a coisa feita com o molde (a casa construída). De uma classe você cria quantos objetos quiser, e cada um tem os seus próprios valores.

  • Atributos (ou campos): o que o objeto tem. Um convidado tem nome, e-mail e idade.
  • Métodos: o que o objeto faz. Um convidado sabe cadastrar() e obterDados().
  • Construtor: a função especial que cria o objeto e preenche os atributos.
Exemplo geral 
class Carro {
  String modelo;              // atributo
  int velocidade = 0;

  Carro(this.modelo);         // construtor: this.modelo guarda o valor direto

  void acelerar(int quanto) { // método
    velocidade += quanto;
  }
}

final a = Carro('Gol');       // objeto 1
final b = Carro('Onix');      // objeto 2, com valores próprios
a.acelerar(30);
print(a.velocidade);          // 30
print(b.velocidade);          // 0
No seu projeto

Cada tabela do banco virou uma classe. Cada linha da tabela vira um objeto quando o programa carrega os dados: a tabela convite tem mais de mil linhas, então a lista convites tem mais de mil objetos Convite.

2. Os 4 pilares da POO

AbstraçãoRepresentar só o que importa do mundo real. Um Convidado tem nome e idade, não tem cor do cabelo.
EncapsulamentoEsconder os dados e controlar o acesso por getters e setters, que validam.
HerançaUma classe aproveita o que outra já tem. Convite "é um" Registro.
PolimorfismoA mesma chamada se comporta de jeitos diferentes, conforme o objeto.

3. Encapsulamento, getters e setters

O problema: se qualquer parte do programa pudesse mexer direto nos dados, alguém poderia colocar idade −5 ou e-mail "abc". O encapsulamento resolve isso: o dado fica privado, e só se mexe nele por métodos que conferem o valor.

Privado com _

Em Dart, um nome que começa com _ só pode ser usado dentro do mesmo arquivo (a mesma "biblioteca"). Não existe a palavra private como em Java: o _ faz esse papel.

Exemplo geral: sem e com encapsulamento 
// SEM encapsulamento: qualquer um estraga o dado
class ContaRuim {
  double saldo = 0;
}
final r = ContaRuim();
r.saldo = -1000;              // ninguém impede!

// COM encapsulamento
class Conta {
  double _saldo = 0;                        // privado

  double get saldo => _saldo;               // GETTER: leitura liberada

  void depositar(double valor) {            // a única forma de aumentar
    if (valor <= 0) throw ArgumentError('Depósito precisa ser positivo');
    _saldo += valor;
  }

  void sacar(double valor) {
    if (valor > _saldo) throw StateError('Saldo insuficiente');
    _saldo -= valor;
  }
}
final c = Conta();
c.depositar(100);
print(c.saldo);               // 100 (pelo getter)
// c.saldo = 5000;           // ERRO: não existe setter, saldo é só leitura

Getter

Um getter é um método que se usa como se fosse um atributo. Ele pode só devolver um campo privado, ou calcular algo na hora.

class Retangulo {
  double largura, altura;
  Retangulo(this.largura, this.altura);

  double get area => largura * altura;   // getter CALCULADO: não guarda nada
}
final r = Retangulo(3, 4);
print(r.area);    // 12 (sem parênteses: parece um campo)
r.largura = 5;
print(r.area);    // 20: sempre atualizado

Setter

Um setter é um método que se usa com =, como se fosse atribuir um campo. Ele é o lugar certo para validar.

class Pessoa {
  int _idade = 0;
  int get idade => _idade;
  set idade(int valor) {
    if (valor < 0 || valor > 130) {
      throw ArgumentError('Idade inválida: $valor');
    }
    _idade = valor;
  }
}

4. Herança

Herança é quando uma classe (filha) recebe tudo o que outra classe (mãe) tem, e acrescenta ou muda o que precisar. A palavra-chave é extends, e o teste é a frase "é um": um Cachorro é um Animal; um Convite é um Registro.

Exemplo geral 
class Animal {
  String nome;
  Animal(this.nome);

  void comer() => print('$nome está comendo');
  String som() => '...';
}

class Cachorro extends Animal {
  Cachorro(super.nome);                 // repassa o nome para o construtor de Animal

  void buscarBolinha() => print('$nome buscou a bolinha');   // só dele

  @override
  String som() => 'Au au';              // muda o que veio do pai
}

final rex = Cachorro('Rex');
rex.comer();          // "Rex está comendo" (herdado, sem escrever de novo)
rex.buscarBolinha();  // "Rex buscou a bolinha" (novo)
print(rex.som());     // "Au au" (sobrescrito)

O que a filha pode fazer

  • Herdar: usar atributos e métodos do pai sem reescrever.
  • Acrescentar: ter atributos e métodos só dela.
  • Sobrescrever (@override): trocar o comportamento de um método do pai.
  • Chamar o pai com super: super.metodo() usa a versão do pai dentro da versão nova.
class Gato extends Animal {
  Gato(super.nome);
  @override
  void comer() {
    super.comer();                       // faz o que o pai fazia...
    print('$nome lambeu o prato');       // ...e acrescenta
  }
}

Regras importantes do Dart

  • Herança simples: uma classe só pode ter um pai com extends. Para reaproveitar código de várias fontes, existem os mixins (seção 7).
  • Construtores não são herdados. Cada filha escreve o seu e chama o do pai, com super.campo ou : super(...).
  • Toda classe herda de Object, mesmo sem escrever extends. É de lá que vêm o toString() e o ==.
No seu projeto
lib/Organizador.dart
class Organizador extends Usuario {        // Organizador É UM Usuario

  int? _idSessao;                           // acrescenta: a sessão de login

5. Polimorfismo

"Muitas formas": a mesma chamada produz comportamentos diferentes, dependendo do objeto que a recebe. Ele funciona por causa de duas coisas juntas: a sobrescrita (@override) e o fato de um objeto filho poder ser guardado numa variável do tipo do pai.

Exemplo geral 
final bichos = <Animal>[Cachorro('Rex'), Gato('Mimi'), Animal('Genérico')];
for (final b in bichos) {
  print('${b.nome}: ${b.som()}');
}
// Rex: Au au
// Mimi: ...        (Gato não sobrescreveu som, usa o do pai)
// Genérico: ...

O laço trata todos como Animal. Na hora de rodar, o Dart descobre o tipo real de cada objeto e chama a versão certa de som(). Isso tem o nome de ligação dinâmica (dynamic dispatch).

Exemplo geral: formas de pagamento 
abstract class Pagamento {
  double valor;
  Pagamento(this.valor);
  double total();                      // cada forma calcula do seu jeito
}
class Pix extends Pagamento {
  Pix(super.valor);
  @override
  double total() => valor * 0.95;       // 5% de desconto
}
class Cartao extends Pagamento {
  int parcelas;
  Cartao(super.valor, this.parcelas);
  @override
  double total() => parcelas > 3 ? valor * 1.10 : valor;   // juros acima de 3x
}

double cobrar(Pagamento p) => p.total();   // não sabe e não precisa saber qual é
cobrar(Pix(100));        // 95.0
cobrar(Cartao(100, 6));  // 110.0

A grande vantagem: para aceitar uma forma de pagamento nova (boleto), basta criar class Boleto extends Pagamento. A função cobrar não muda nada.

No seu projeto 
final coisas = <Registro>[evento, convite, checkin, itemDaFila];
for (final r in coisas) {
  print(r.obterDados());   // cada um responde do SEU jeito
}
// ID: 1001 | Nome: Casamento...      (Evento)
// Convite #5 | Convidado: Ana...     (Convite)
// 1º | Bruno (id 1200) | na fila...  (ItemListaEspera)

E tem um polimorfismo "escondido": o print(convite) chama toString(), que está no Registro e chama obterDados(). Quem responde é a versão do Convite. Um método do pai chamando um método que só o filho sabe fazer é um padrão conhecido como Template Method.

E a sobrecarga (overloading)? Em Java, dá para ter dois métodos com o mesmo nome e parâmetros diferentes. Dart não permite isso. No lugar, usa parâmetros opcionais e nomeados, ou construtores nomeados, como Convite(...) e Convite.doBanco(...).

6. Abstração e classes abstratas

Abstração é escolher o que importa. Num sistema de eventos, um Convidado tem nome, e-mail, telefone, idade e assento. A cor favorita dele não importa, então não entra na classe.

Uma classe abstrata (abstract class) é um molde que não pode virar objeto. Ela existe para ser herdada, e pode ter métodos abstratos: métodos sem corpo, que cada filha é obrigada a escrever.

abstract class Forma {
  double area();              // abstrato: sem corpo
  void descrever() => print('Área: ${area()}');   // concreto: usa o abstrato
}
class Quadrado extends Forma {
  double lado;
  Quadrado(this.lado);
  @override
  double area() => lado * lado;   // obrigado a escrever, ou não compila
}
// Forma();   // ERRO: não se cria objeto de classe abstrata
No seu projeto
lib/Registro.dart
abstract class Registro {
  int? _idBanco;
  Registro({int? idBanco}) : _idBanco = idBanco;
  int? get idBanco => _idBanco;
  set idBanco(int? valor) => _idBanco = valor;

  String obterDados();                     // abstrato: cada entidade se descreve

  @override
  String toString() => obterDados();       // concreto: usa o abstrato
}
  • Por que existe: 7 classes precisam de idBanco. Sem o Registro, o mesmo código estaria repetido 7 vezes.
  • Por que é abstrata: não existe "um registro" sozinho. Ou é um Evento, ou um Convite, ou outra entidade.
  • Por que obterDados() é abstrato: é uma regra para todo mundo. Quando a classe ItemListaEspera foi criada, o próprio Dart obrigou a escrever o obterDados() dela.
  • O Usuario também é abstrato e não escreve o obterDados(). Isso é permitido porque ele é abstrato: a obrigação passa para Organizador e Convidado.

7. Interfaces e mixins

implements: "eu prometo ter estes métodos"

Em Dart, toda classe também funciona como interface. Com implements, a classe promete ter todos os métodos e atributos da outra, mas não herda nenhum código: precisa escrever tudo.

abstract class Exportavel {
  String paraCsv();
}
class Relatorio implements Exportavel {
  @override
  String paraCsv() => 'evento;convidados\nFesta;120';
}
  • extends: herda o código. Só um pai.
  • implements: só a promessa. Pode implementar várias interfaces.

Mixin: um "pacote de habilidades"

Um mixin é um bloco de código que você acrescenta a qualquer classe com with, sem herança. Ele resolve o "só um pai" quando várias classes precisam da mesma habilidade.

mixin Auditavel {
  final List<String> log = [];
  void registrar(String acao) => log.add('${DateTime.now()}: $acao');
}
class Evento2 extends Registro with Auditavel { ... }
// Evento2 é um Registro E ganha registrar() do mixin

A v3.4 não usa mixins nem implements, mas a versão Flutter do app usa: with SingleTickerProviderStateMixin na animação do nome.

8. Composição: "tem um"

Nem tudo é herança. Quando a frase certa é "tem um", o certo é guardar um objeto dentro do outro. Isso se chama composição (ou associação).

lib/Convite.dart
class Convite extends Registro {   // Convite É UM Registro (herança)
  StatusConfirmacao _status;
  final Evento _evento;            // Convite TEM UM Evento (composição)
  final Convidado _convidado;      // Convite TEM UM Convidado (composição)
  ...
}

Seria errado escrever Convite extends Evento, porque um convite não é um evento. A composição espelha as chaves estrangeiras do banco: convite.evento_idevento no MySQL vira o atributo _evento no Dart. Assim você escreve convite.evento.nomeEvento em vez de procurar o evento pelo id.

Outros exemplos de composição no projeto: Checkin tem um Convite; ItemListaEspera tem um Evento e um Convidado; Evento tem um HistoricoEvento e uma Mesa padrão.

9. static, factory e const

static: pertence à classe, não ao objeto

class ConfigBanco {
  static String host = 'localhost';   // um só para o programa inteiro
}
ConfigBanco.host;                      // usa sem criar objeto

No projeto: ConfigBanco guarda a configuração da conexão em campos static. Evento._limiteValido é um método static, porque validar um número não depende de um evento específico.

Construtor nomeado

Uma classe pode ter vários construtores com nomes diferentes. No projeto, todas as entidades têm o normal, para criar um objeto novo, e o doBanco, para montar um objeto a partir de uma linha do MySQL.

factory: construtor que decide ou calcula

factory VagasEvento.calcular(Evento evento, List<Convite> convites,
    List<ItemListaEspera> fila) {
  final ativos = convites.where(...).length;   // faz a conta ANTES
  return VagasEvento(limite: ..., convitesAtivos: ativos, pessoasNaFila: ...);
}

Um construtor normal só preenche campos. Um factory pode fazer contas, escolher que objeto devolver ou até devolver um objeto já existente.

Construtor const

class EstatisticasEvento {
  final int totalConvites;
  ...
  const EstatisticasEvento({required this.totalConvites, ...});
}

Quando todos os campos são final, o construtor pode ser const. O objeto fica imutável: depois de criado, não muda. Isso é ótimo para resultados de cálculo, que não devem ser alterados.

4. Funções como valores

Em Dart, uma função é um valor como qualquer outro: pode ser guardada numa variável e passada como parâmetro.

void repetir(int vezes, void Function(int) acao) {

}
repetir(3, (i) => print('volta $i'));

No projeto, o _transacao recebe a operação como parâmetro: _transacao(() async { ... }). As funções where, map e any também recebem funções.

6. async, await e Future

Algumas tarefas demoram: falar com o banco, esperar um segundo, ler um arquivo. Em vez de travar o programa, o Dart usa Future: "um valor que vai chegar depois".

Future<String> buscarNome() async {
  await Future.delayed(const Duration(seconds: 1));   // finge demorar
  return 'Ana';
}

Future<void> main() async {
  print('Buscando...');
  final nome = await buscarNome();   // espera o valor chegar
  print(nome);
}
  • async marca uma função que tem espera dentro dela.
  • await espera um Future terminar antes de seguir para a próxima linha.
  • Uma função async sempre devolve um Future.

No projeto, quase toda função do banco.dart é async, porque cada uma espera o MariaDB responder. O main do programa também é async.

7. Exceções: tratando erros

try {
  final n = int.parse('abc');      // lança FormatException
} on FormatException {
  print('Isso não é número');      // pega só esse tipo de erro
} catch (e) {
  print('Outro erro: $e');         // pega qualquer outro
} finally {
  print('Sempre roda');            // com erro ou sem erro
}
No seu projeto
  • throw ArgumentError(...) nos setters, quando um dado é inválido.
  • try / catch nas telas, para mostrar "Erro ao salvar..." sem derrubar o programa.
  • finally no main, para sempre fechar a conexão com o banco, mesmo se der erro.
  • rethrow no _transacao: depois do ROLLBACK, o erro é jogado de novo para quem chamou também ficar sabendo.
  • int.tryParse em vez de int.parse: devolve null em vez de lançar erro quando o usuário digita letras no menu.

1. Arquitetura: como as peças se encaixam

O programa roda no terminal e conversa direto com o MariaDB pela biblioteca mysql_client, sem API no meio. Ele é dividido em três camadas, e cada camada tem uma função só.

1

4. O banco.dart por dentro

Conectar direto ao MySQL

lib/banco.dart
final conn = await MySQLConnection.createConnection(
  host: ConfigBanco.host, port: ConfigBanco.port,
  userName: ConfigBanco.usuario, password: ConfigBanco.senha,
  databaseName: ConfigBanco.nomeBanco, secure: false,

O ConfigBanco.carregar() lê esses dados do config.json, ou das variáveis DB_HOST, DB_PORT e outras, se você as passar.

Os 4 "ajudantes" privados

  • _consultar(sql, params): para SELECT. Devolve uma lista de linhas, e cada linha é um Map com coluna e valor.
  • _inserir(sql, params): para INSERT. Devolve o id que o banco gerou (lastInsertID).
  • _executar(sql, params): para UPDATE e DELETE.
  • _transacao(() async {...}): roda vários comandos como um só.
Future<T> _transacao<T>(Future<T> Function() operacao) async {
  await _executar('START TRANSACTION');
  try {
    final resultado = await operacao();
    await _executar('COMMIT');      // deu tudo certo: grava
    return resultado;
  } catch (_) {
    await _executar('ROLLBACK');    // algo falhou: desfaz TUDO
    rethrow;
  }
}

Este pequeno trecho junta vários conceitos: generics (<T>), função como parâmetro (operacao), async/await, try/catch e rethrow.

Parâmetros com :nome, a proteção contra SQL Injection

'SELECT ... FROM usuario WHERE email = :email', {'email': email}

O valor nunca é colado dentro do texto do SQL. A biblioteca envia o valor à parte, então se alguém digitar ' OR 1=1 -- como e-mail, aquilo é tratado como texto comum, não como comando.

De linha do banco para objeto

for (final l in linhas) {                    // cada l é um Map: coluna → valor
  fila.add(ItemListaEspera.doBanco(
    idBanco: _int(l['id']),                  // texto '12' vira int 12
    evento: evento,
    convidado: convidado,
    posicao: _int(l['posicao']),
    criadoEm: DateTime.parse(l['criado_em']!),
  ));
}

A biblioteca devolve tudo como texto. O código converte cada coluna para o tipo certo (int, DateTime) e usa o construtor doBanco. Essa "tradução" entre tabelas e objetos tem o nome de mapeamento objeto-relacional.

5. O que mudou na v3.4

5.1 A troca de nomes: organizador virou usuario

  • Foram 13 trechos de SQL no banco.dart: organizador → usuario e id_organizador → id_usuario.
  • Nas tabelas login_registro, sessao_login e troca_senha: organizador_id_organizador → usuario_id_usuario.
  • Na tabela evento, a coluna continua organizador_id_organizador, porque no banco ela não mudou.

5.2 Evento.dart: o limite de vagas

lib/Evento.dart
int? _limiteConvidados; // null = sem limite

int? get limiteConvidados => _limiteConvidados;
set limiteConvidados(int? valor) => _limiteConvidados = _limiteValido(valor);

static int? _limiteValido(int? valor) {
  if (valor != null && valor < 1) {
    throw ArgumentError('O limite de convidados precisa ser pelo menos 1: $valor');
  }
  return valor;
}
  • Encapsulamento: o setter impede limite 0 ou negativo.
  • static: validar um número não depende de um evento específico.
  • int?: o null representa "sem limite", que é o caso dos eventos antigos.

5.3 ListaEspera.dart (novo): a classe ItemListaEspera

Aqui estão quatro conceitos juntos: herança (extends Registro), composição (tem um Evento e um Convidado), encapsulamento (campos privados; só a posição tem setter, que valida) e polimorfismo (@override obterDados).

5.4 vagas_evento.dart (novo): o cálculo de vagas em Dart

Substitui a VIEW do banco. Convite "ativo" é qualquer convite que não foi recusado, porque ele ainda ocupa um lugar.

lib/vagas_evento.dart
factory VagasEvento.calcular(Evento evento, List<Convite> convites,
    List<ItemListaEspera> fila) {
  final ativos = convites
      .where((c) => c.evento == evento && c.status != StatusConfirmacao.recusado)
      .length;
  final naFila = fila.where((item) => item.evento == evento).length;
  return VagasEvento(limite: evento.limiteConvidados,
      convitesAtivos: ativos, pessoasNaFila: naFila);
}

int? get vagasLivres {
  final l = limite;
  if (l == null) return null;
  final sobra = l - convitesAtivos;
  return sobra < 0 ? 0 : sobra;      // nunca negativo
}

bool get lotado => temLimite && vagasLivres == 0;

Por que promover é uma transação: são 4 passos. Se a luz caísse depois de criar o convite, mas antes de tirar a pessoa da fila, ela ficaria com convite e na fila. Com a transação, ou tudo acontece, ou nada acontece.

O SET @historico_pelo_codigo = 1 e a trigger de reserva

Agora quem grava o histórico é o código. A trigger do banco foi alterada para só gravar WHERE @historico_pelo_codigo IS NULL.

Uma variável com @ vale só para a conexão que a criou. A v3.4 marca a variável, então nessa conexão a trigger fica quieta e não duplica o histórico. O app com API não marca, então para ele a trigger continua gravando.

Por que existe o _tirarDaFilaEmMassa: as chaves estrangeiras da lista_espera têm ON DELETE CASCADE. Se um convidado for apagado, o banco apaga as linhas dele na fila sozinho, e nesse caso a trigger não dispara. Por isso o código registra essas saídas no histórico antes de apagar.

5.6 O menu 11 e a ligação com os convites

As opções do menu 11: 1 ver a fila e as vagas · 2 definir ou alterar o limite (0 = sem limite) · 3 colocar pessoa na fila · 4 promover da fila · 5 remover pessoa da fila · 6 ver histórico · 7 voltar. Qualquer usuário logado pode usar: não há if (ehAdministrador) nele.

No menu de convites:

  • Convidar com o evento lotado: o programa oferece colocar a pessoa na fila.
  • Cadastrar alguém novo com o evento lotado: a pessoa é cadastrada e já vai para a fila.
  • Recusar um convite: abriu uma vaga, então o programa oferece a vaga ao 1º da fila.
  • Reativar um convite recusado com o evento lotado: é bloqueado, porque passaria do limite.
  • Quem está na fila não aparece em "convidar": só sai da fila pela promoção, para respeitar a ordem.

1. Exercícios com resposta

1. Qual é o resultado de 17 % 5 e de 17 ~/ 5?

Resposta: 17 % 5 = 2 (o resto) e 17 ~/ 5 = 3 (a divisão inteira), porque 5 × 3 = 15 e sobram 2.

2. No login, por que existe org ??= await _rodada(...) em vez de chamar a segunda rodada sempre?

Resposta: o ??= só executa se org for null. Se o usuário acertou na primeira rodada, a segunda nem roda.

3. Escreva um getter estaCheio para uma classe Onibus que tem int lugares e int passageiros.

Resposta: 
bool get estaCheio => passageiros >= lugares;

4. Escreva um setter para passageiros que não aceite número negativo nem mais passageiros que lugares.

Resposta: 
int _passageiros = 0;
int get passageiros => _passageiros;
set passageiros(int valor) {
  if (valor < 0 || valor > lugares) {
    throw ArgumentError('Passageiros inválidos: $valor');
  }
  _passageiros = valor;
}

5. O que acontece se você criar class Pulseira extends Registro {} sem mais nada?

Resposta: o código não compila. Registro tem o método abstrato obterDados(), e toda classe concreta que herda dele é obrigada a implementá-lo com @override.

6. "Um Check-in é um Convite"? Deveria ser Checkin extends Convite?

Resposta: não. Um check-in tem um convite (composição). Por isso Checkin herda de Registro e guarda o convite no atributo _convite.

7. Faça o teste de mesa da renumeração para a fila 1-Ana, 2-Bruno, 3-Carla quando a Ana sai. Quem recebe UPDATE?

Resposta: Ana é pulada (continue), o contador continua em 1. Bruno: 2 != 1, vira 1; contador vai a 2. Carla: 3 != 2, vira 2. Resultado: 1-Bruno, 2-Carla. Bruno e Carla recebem UPDATE.

8. Um evento tem limite 50, 52 convites ativos e 3 pessoas na fila. Quanto valem vagasLivres, lotado e cabemDaFila?

Resposta: a sobra seria −2, mas o código nunca deixa negativo, então vagasLivres = 0. Como tem limite e não sobra vaga, lotado = true. E cabemDaFila = 0.

9. Por que a função promoverDaListaEspera usa _transacao?

Resposta: porque ela faz 4 operações que precisam acontecer juntas (criar convite, gravar histórico, apagar da fila, renumerar). Se uma falhar, o ROLLBACK desfaz as outras e o banco não fica com dados pela metade.

10. Crie uma classe Palestrante que herda de Usuario, tem um tema de palestra e se descreve com obterDados().

Resposta:

  Palestrante({super.idBanco, super.nome, super.email, required String tema})
      : _tema = tema;

  String get tema => _tema;

2. Glossário

Algoritmo
Sequência de passos para resolver um problema.
Variável
Espaço com nome na memória que guarda um valor de um tipo.
Tipo
Diz que espécie de valor uma variável guarda: int, String, bool...
Null safety
Regra do Dart que obriga a marcar com ? o que pode ficar vazio.
Laço (loop)
Estrutura que repete um bloco: for, while, do-while.
Função
Bloco de código com nome, que recebe parâmetros e pode devolver um valor.
Lambda
Função anônima e curta, como (c) => c.presente.
Classe
Molde que define atributos e métodos.
Objeto (instância)
Algo criado a partir de uma classe, com valores próprios.
Construtor
Função especial que cria o objeto. Pode ser nomeado, factory ou const.

Esconder os dados (com _) e controlar o acesso por getters e setters.

Classe filha recebe o que a mãe tem (extends). Relação "é um".
Composição
Um objeto guardado dentro do outro. Relação "tem um".
Polimorfismo
A mesma chamada tem comportamentos diferentes conforme o objeto.
Sobrescrita (@override)
A filha troca a versão de um método herdado.

Molde que não vira objeto e pode ter métodos sem corpo.

Promessa de ter certos métodos, sem herdar código.

static

enum

3. Resumo para os professores

"O sistema roda no terminal e conecta direto ao MariaDB com a biblioteca mysql_client, sem API. Ele é dividido em três camadas: telas (menus), modelos e regras (classes Dart) e acesso ao banco (banco.dart), onde todo o SQL usa parâmetros nomeados contra SQL Injection.

As entidades herdam da classe abstrata Registro, que centraliza o idBanco e obriga cada uma a implementar obterDados(). Isso é herança e polimorfismo. Organizador e Convidado herdam de Usuario, também abstrata, que valida nome e e-mail nos setters. Os relacionamentos do banco viram composição: um Convite tem um Evento e um Convidado.

A lógica aparece no menu (laço com switch), no login (contadores, bloqueio e estados), na validação de CPF (soma ponderada e resto da divisão), nas estatísticas e na economia de insumos (fórmulas com proteção contra divisão por zero).

Na versão 3.4 criei a lista de espera com a regra no código: o limite de vagas é um campo do Evento com setter validado, e a classe VagasEvento calcula as vagas a partir dos convites não recusados. Com o evento lotado, a pessoa vai para o fim da fila. Quando alguém recusa, o primeiro da fila recebe a vaga. Promover e remover são transações, com commit ou rollback, que gravam o histórico e renumeram a fila. O cálculo é testado com 12 testes automáticos, sem precisar do banco."

Perguntas que podem aparecer

  • "Qual a diferença entre herança e composição?" Herança é "é um" (Convite extends Registro); composição é "tem um" (o convite guarda um Evento).
  • "Onde está o polimorfismo?" No obterDados(): todas as entidades são tratadas como Registro, e cada uma responde do seu jeito. O print(objeto) mostra isso.
  • "Por que usar getter e setter?" Para validar os dados. O setter de limiteConvidados recusa 0 ou negativo, e o de email recusa e-mail inválido.
  • "Por que não deixou tudo no banco?" Porque a regra fica visível e testável no código. O banco continua garantindo a integridade: chaves estrangeiras, o UNIQUE e a trigger de reserva para outros programas.
  • "O que acontece se cair a conexão no meio de uma promoção?" O ROLLBACK desfaz tudo, então nenhum dado fica pela metade.
  • "Como a senha é guardada?" Como hash bcrypt. No login, senhaConfere compara a senha digitada com o hash, e a senha real nunca fica gravada.
  • "Como o administrador é identificado?" Pelo ehAdministrador do Organizador.dart, que hoje compara com ids fixos (1000 e 1005). O banco já tem a coluna administrador, mas a v3.4 ainda não lê essa coluna. É um ponto de melhoria que você pode citar.
